01 / System architecture

Two connected data flows

A knowledge refresh prepares the vector index. At runtime, visitor questions retrieve relevant passages and use them to ground the chat model's answer.

Implementation-based overview
A Query-time response
Live application · Gradio hosted on Render
  1. STEP 01◉

    Visitor asks

    Question enters from a desktop or mobile browser.

  2. STEP 02▣

    Gradio on Render

    Python app receives the question and recent conversation.

  3. STEP 03✧

    Semantic retrieval

    Titan V2 embeds the query; NumPy ranks local passages by cosine similarity.

  4. STEP 04≡

    Evidence assembly

    Top matches, source links and bounded chat history become model context.

  5. STEP 05✦

    Chat model

    OpenAI-compatible completion endpoint generates a grounded reply.

  6. STEP 06✓

    Answer + actions

    Response returns to Gradio; optional approved tools can notify the owner.

Powered by the same semantic embedding space
B Knowledge ingestion and refresh
Owner-initiated refresh · snapshot loaded by app
  1. STEP 01▤

    Knowledge sources

    Profile, summary, selected GitHub projects, Medium articles and YouTube metadata or captions.

  2. STEP 02▥

    Collect + chunk

    Refresh script gathers text and splits it into bounded, overlapping passages.

  3. STEP 03✧

    Amazon Bedrock

    Titan Text Embeddings V2 converts passages into normalized 1024D vectors.

  4. STEP 04▦

    Local vector index

    Validated NumPy snapshot stores vectors and source metadata for exact semantic search.

↑ The runtime retrieval step searches the refreshed local vector index. No hosted vector database is required.

✦ What makes this RAG?

The model is given retrieved passages from curated professional sources instead of a full profile pasted into every request. It is instructed not to invent experience, to distinguish projects from production work and to cite source URLs when available.

↗ Optional owner notifications

The app exposes allowlisted functions for contact requests and unanswered questions. These can send notifications through Pushover; they are not part of every reply.

02 / Technology stack

Purpose-built, not overbuilt

Simple pieces, clear responsibilities and a retrieval layer that can be inspected and evaluated independently.

Presentation

Gradio + Python

Conversational UI, suggested questions and application orchestration.

Hosting

Render

Hosts the running AI application; this architecture page is static and can live on GitHub Pages.

AI embeddings

Amazon Bedrock Titan V2

Produces the same 1024-dimensional semantic vectors for source passages and user queries.

Retrieval

NumPy + cosine similarity

A self-contained local vector snapshot; no external vector database or keyword-routing layer.

Generation

Configurable chat model

OpenAI-compatible Chat Completions API. Model and endpoint are selected through configuration.

Actions

Pushover

Optional notifications for voluntary contact requests and knowledge gaps.

03 / Engineering choices

Practical design boundaries

The retrieval workflow is intentionally bounded, verifiable and straightforward to operate.

Evidence first

Relevant context only

At most six retrieved passages, with explicit context and conversation-history limits.

Index management

Controlled refresh

Embeddings are cached and the local index is replaced only after a successful validated build.

Operations

Bounded tool execution

Allowlisted actions and capped tool rounds. Raw visitor content and credentials are not intentionally logged.
